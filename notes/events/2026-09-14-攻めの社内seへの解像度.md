# 「攻めの社内SE」への解像度を高めないと

## 出来事

「攻めの社内SE」というキャリアの選択肢が頭にある。ただ、今の理解度だと解像度が低く、実態がぼんやりしたまま「良さそう」と思っているだけの状態だと気づいた。

## 思考・感情

- 解像度を上げないと、それが本当に自分にとって理想の仕事なのか判断できない。
- 問い1: 「攻めの社内SE」は自分にとって理想の仕事なのか?
- 問い2: 理想だとして、今の自分に足りない経験は何か?
- どちらも、今の自分の中に答えがあるわけではなく、情報収集と自己分析をしないと言語化できなさそう。

## 気づき・次のアクション

- 「攻めの社内SE」の実態(業務内容・求められるスキル)を調べて解像度を上げる必要がある。 -> #7

## 追記(2026-09-14)

社内SE転職ナビにキャリア相談を依頼した。次は相談事項を軽くまとめる。

### 相談事項(ドラフト)

目的: 「攻めの社内SE」が自分にとって理想の仕事か、今の自分に足りない経験は何かを判断する材料を得る。

- 「攻めの社内SE」の実態: 具体的にどんな業務・裁量・「攻め方」を指すことが多いか(受け身の社内SEとの違い)
- どんな会社・業界・企業フェーズに「攻めの社内SE」ポジションが多いか
- 転職市場感: 求人数、年収レンジ、選考でよく見られる難易度・競争率
- 自分の現在の経験(職種・経験年数などは相談時に伝える)がどこまで通用するか、プラスに働く経験・マイナスに働きやすい経験
- 足りない経験を埋めるために、転職前にやっておいた方がよいこと(資格、実務、副業、学習など)
- 「攻めの社内SE」として活躍している人によくある経歴・バックグラウンド
- 入社後にイメージと実態でギャップが生まれやすいポイント・失敗しやすいパターン

-> 相談前に、自分の現職の経験・スキルを一言でまとめたメモも用意しておくと、より具体的な回答をもらえそう。

### 「理想」の中身(言語化)

- ベンチャーの、キラキラ・挑戦的な雰囲気が良い。
- Zenn発信やLT登壇など、社外に発信するカルチャーがある環境がgood。
- つまり「守りの社内SE」ではなく、技術的に前に出て挑戦・発信していける環境そのものに惹かれている面がありそう。

### 相談事項に追加

- ベンチャー気質(挑戦的・スピード感)で「攻めの社内SE」ポジションがある会社の見分け方・具体例
- 発信文化(Zenn執筆・LT登壇など)がある社内SE組織はどれくらいあるか、そういう文化があるかを求人票や面接でどう見極めるか

### 自己ツッコミ(2026-09-14)

現時点で「何言ってんねん」となりそうな点をClaudeに壁打ちしてもらった。

1. 「職務」と「社風」を混ぜている。「攻めの社内SE」(業務・IT導入への関わり方)と「ベンチャーのキラキラ感」「Zenn/LT」(会社のカルチャー)は別軸。両方揃う求人はかなり狭い交差点になりうる。→ ここが一番効く指摘。
2. Zenn/LTのような発信文化は、社内SEよりプロダクトエンジニア組織の方が一般的。本当に惹かれているのが「発信できる技術カルチャー」なら、社内SEというくくりにこだわらずコーポレートエンジニアリング/Platform Engineeringなど隣接職種も比較対象に入れるべきかもしれない。
3. 相談先の「社内SE転職ナビ」自体が「攻めの社内SE」を売り文句にしているエージェントなので、そこで聞く「実態」はポジショントーク込みの可能性がある。実際に働いている人への直接ヒアリングも並行すべき(#7で元々挙げていたはず)。
4. 「キラキラ」の中身が、SNSや採用ページなど外から見た印象ベースのままで、中の人の実態(忙しさ・裁量)とはまだ解像度が低い。
5. 自分の現在の経験の棚卸しがまだ手つかず。問い2(足りない経験は何か)に答えるための土台が埋まっていない。相談前にここを埋める必要がある。

### 隣接職種の調査(2026-09-14)

指摘2(発信文化は社内SEよりプロダクトエンジニア組織寄り)を受けて、隣接職種を整理した。

- **コーポレートエンジニア**: SmartHR・LayerX・Classi・マネーフォワードなど日本のSaaS/スタートアップ界隈で使われる職種名で、実質「攻めの社内SE」とほぼ同義。SaaS連携・自動化・Terraformでの社内インフラのコード化などエンジニアリング色が強く、「Corporate Engineering Meetup」のような勉強会やZennの「コーポレートエンジニアリング」タグでの発信も実際に盛ん。**本命の可能性が高い。**
- **Platform Engineer / SRE**: 対象が全社員ではなく自社の開発エンジニア組織。発信文化は強いが「社内SE」という括りからは外れる。
- **BizOps/RevOps**: 営業・マーケ向けのSFA/CRM運用。攻めの要素はあるがエンジニアリング色・発信文化との相性は薄め。
- **IT戦略・DX推進職**: 経営に近い企画職。キラキラ感はあるが手を動かす度合いは低く、発信文化との相性は会社・個人次第。

比較すると、技術度・発信文化との相性ともに高いのは「コーポレートエンジニア」。求人検索や社内SE転職ナビへの相談で、「社内SE」だけでなく「コーポレートエンジニア」というキーワードでも探すのが実用的な次の一歩。

### 「理想」の再定義: 職種名より本質(2026-09-15)

「社内SE」「コーポレートエンジニア」という職種名にこだわっていたが、話しているうちに本質が見えてきた。

**本質的な希望**: 着想(自分のアイデア)を活かしつつ、事業会社(受託/SIerではなく自社サービスを持つ会社)で裁量を持って働くこと。「社内の業務改善」という仕事内容そのものへのこだわりではなく、社内SE/コーポレートエンジニアはその手段の一つに過ぎなかった。

**では、プロダクト開発エンジニア(事業会社の自社サービス開発)は選択肢に入るか?**

→ 直感的に「自分の経験ではハードルが高い」と感じており、これは妥当な判断だと思う。理由:
- 実務経験はMagic XPA(独自ローコードツール、3年)・Oracle/SQL Server中心で、業務システム/SIer領域としては強いが、事業会社の自社開発が求める「モダンなWeb開発力」としてはほぼアピールにならない
- TypeScript実務は2026年2月からの半年程度(直近の主担当もOutSystemsというローコード)
- Reactの実務経験はゼロ(hiramecoは個人開発)

つまり「ローコード/業務パッケージ開発の経験は豊富だが、モダンなWeb開発の実務経験がほぼない」状態。プロダクトエンジニア直接応募だと、給与・裁量が低めになりがちな「未経験可」枠を狙うことになりやすく、希望の「裁量を持って働く」とは相性が悪い可能性が高い。

一方、社内SE/コーポレートエンジニアは、業務要件を汲み取る力・顧客折衝・上流〜下流の一貫経験がそのまま強みとして評価されやすく、実務経験ギャップが相対的に小さい。SaaS連携やAPI活用など軽めの開発を伴うことも多く、モダン技術に触れながら裁量を持って働くための橋渡しとしても機能しうる。

**選択肢の整理**
1. 社内SE/コーポレートエンジニアを本命にする(現状の検討路線)。実務経験ギャップが相対的に小さく、現実的な最短ルート。
2. プロダクトエンジニア直接応募。「着想・裁量」という本質にはより合うが、実務経験ギャップが大きく、給与・裁量を妥協した「未経験可」枠になりやすい。
3. 段階的に狙う。まずコーポレートエンジニア等で事業会社に入り、社内でモダン技術・プロダクト開発に近い経験を積んでから、社内異動や次の転職でプロダクト側に寄せる。

現状のスキルセットでは 1→3 のルートが現実的、という結論。

-> エージェント相談では、コーポレートエンジニア経由でプロダクト開発側へのキャリアパス(社内異動事例など)があるかも聞いてみる。 -> #7

### 判断基準の確定(2026-09-15)

一連の検討を経て、職種名(社内SE/コーポレートエンジニア)そのものにはこだわらないという結論に至った。**「着想(自分のアイデア)を活かせる裁量が実際にあるかどうか」が会社選びの最重要基準**。社内SE/コーポレートエンジニアという肩書きでも、経営・事業側からの指示を実行するだけの立場か、自分から課題を見つけて提案・実現できる立場かで裁量は全く違うため、そこを見極める必要がある。

**相談事項に追加**
- 「攻めの社内SE/コーポレートエンジニア」といっても、経営・事業側からの指示を実行する立場と、自分から課題を見つけて提案・実現する立場とでは裁量が全然違うと思うが、どちらの求人が多いか、見分け方はあるか
- 面接や求人票で「着想を活かせる裁量があるかどうか」を見極めるには、何を聞く/見るのが良いか

-> 相談時にこの2点を必ず確認する。 -> #7

### 社内SE転職ナビへの相談結果(2026-09-16)

- 「攻めの情シス」と言っても、実態は泥臭いヘルプデスク・キッティング業務が中心なことが多い、との回答。自己ツッコミ(3, 4)の裏付けとなった。
- 本当に着想を活かしたいなら、IT企画やコンサルの方が良いかも、との提案。
- 一方でIT企画は社内SEからの社内ステップアップが主流で未経験の直接入社は狭き門、コンサルは「事業会社の中の人として裁量を持つ」という軸とはややズレる、という懸念もあり、即採用ではなく検討材料として保留。

-> 「社内SEで実務経験を積みつつ、企画寄りの動き方を掴んでIT企画にステップアップする」段階的ルートを軸に考える。 -> #7
